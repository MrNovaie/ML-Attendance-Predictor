v0.5

  transaction, so a bad file changes nothing. Refuses a non-empty database unless --replace. Logins are not in the backup.

v1.0  (the finished version for its planned use: a small team on a private network)
- AM/PM split: "Partial Day" (2) became "AM (In)" (2) and "PM (In)" (3). The status table lives in one place
  (STATUSES in users.py); the CHECK constraint, API checks, model labels, backup restore and log wording read it. Startup
  rebuilds attendance_record by itself (one transaction, every row kept). Old Partial Day rows become AM only.
- Last-admin protection: DELETE /api/users/<id> deletes first, counts the admins while holding SQLite's write lock, and
  rolls back with 409 if none is left, so two admins cannot delete each other.
- Activity log, reading: GET /api/activity-log (filters admin, person, action, from, to; paging with before and limit),
  GET /api/activity-log/verify (chain check) and GET /api/activity-log.csv (same filters, formula-safe, UTF-8 with BOM).
  One row per fact; neighbouring rows are grouped only on screen. Plain-sentence wording for every action (describe).
  Activity log screen in the app (admins): chain banner, filters, Load older entries, Refresh, Download CSV.
- Deployment settings: CORS_ORIGIN, VITE_API_URL, COOKIE_SECURE, HOST and PORT; backend/.env and frontend/.env with
  .env.example templates; the server refuses to start in production without SECRET_KEY, ACTIVITY_LOG_KEY or CORS_ORIGIN;
  debug mode off in production. README: "Deploying on a private network" (no CSRF protection or rate limiting: keep it
  off the open internet).
- Housekeeping: Not Recorded wording, AttendanceUtils import casing, .gitignore additions, GPL v3.0 licence decided,
  README screenshots, admin.py dropped from the README layout.

v1.x

1. Stale-board warning
   With 10 admins, two will eventually edit the same day and the last save silently wins. Needs a small backend change (a
   way to tell that a day changed since the board loaded, for example the newest updated_at for that date, sent back with
   the save and compared; answer 409 with the names of whoever changed it) and a frontend message on the board. Decide the
   design first.

2. A production server and HTTPS
   gunicorn (Linux) or waitress (Windows) behind a reverse proxy, a Dockerfile, SQLite WAL mode.
   - Move the startup steps (the ensure_* calls in the __main__ block of app.py) into one function that both
     `python app.py` and a wsgi.py call, so a production server runs them too. test_schema.py already checks that every
     ensure_* function is called from __main__; point it at the new function.
   - Make the model-cache write atomic (write to a temporary file, then rename). Two workers retraining at once can leave a
     half-written models.joblib.

3. CSRF protection and login rate limiting
   What stands between this app and the open internet. Also the login timing leak: /api/login answers faster for an
   unknown username (compare against a dummy hash).

4. Scheduled backup, and the log's off-server anchor
   A scheduled job that copies attendance.db and the CSV backup, and saves activity_log.anchor() (the newest seq and hash)
   somewhere off the server. Then pass that copy to verify_chain(anchor=...) and report tail_checked true, so rows cut off
   the end of the log are noticed.

5. Frontend tests and CI
   - Component tests with Vitest + jsdom: the un-record warning, the tally, the cutoff lock on the user page, the People
     section, and the Activity log helpers (buildLogQuery, groupEntries, formatLogTime are pure functions).
   - A few browser flows with Playwright: drag and drop (mouse and touch), un-record with the warning, the admin sections
     (including the Activity log), the phone layout.
   - Add these to the GitHub Actions workflow (it already runs pytest and the frontend build). Fix the 4 older lint errors
     (React rule against setting state inside an effect, in App.jsx, AttendanceForm.jsx and UserManagement.jsx), then add
     npm run lint to CI.

6. More settings in .env
   TIMEZONE_OFFSET_HOURS (8), SELF_SERVICE_CUTOFF ("08:15"), DEPARTMENTS (comma-separated) and DEFAULT_DEPARTMENT (Holding),
   read inside create_app with today's values as defaults, and validated at startup (offset an integer from -12 to 14,
   cutoff matches HH:MM, department list not empty, default in the list). Tests must set them explicitly. If the offset
   becomes changeable, the log's From/To filters (which compare the stored time as text) assume one offset for every row.
   STATUSES and the CHECK constraint do NOT move into .env: they have to change together.
